.. _python:

Python Bindings
===============

Parthenon provides optional `nanobind <https://github.com/wjakob/nanobind>`_ bindings
that allow the setup of a simulation (input parameters, packages, problem generator, and
the main program) to be written in Python, while the packages and drivers that evolve
the simulation remain in C++.

Building
--------

The bindings are enabled with ``-DPARTHENON_ENABLE_PYTHON=ON``. nanobind is included as
a git submodule (``external/nanobind``) that has its own submodules, so it must be
checked out with

.. code:: bash

   git submodule update --init --recursive

With ``PARTHENON_USE_SYSTEM_PACKAGES=ON`` an installed nanobind is used if it is found.
Python (3.9 or newer, with development headers) is found with CMake's ``FindPython``;
set ``Python_EXECUTABLE`` to choose an interpreter.

Parthenon and Kokkos are compiled as position independent code (with
``PARTHENON_IMPORT_KOKKOS=ON``, the imported Kokkos must have been built that way) and
linked into each application's Python module, together with the core Parthenon
bindings. Since each module contains its own copy of Parthenon and Kokkos, only one such
module should be loaded in a Python process.

Application packages
--------------------

A code binds its C++ components (packages, drivers, and anything else it wants to call
from Python) in its own module, and ``parthenon_add_python_module`` from
``cmake/ParthenonPython.cmake`` builds it into an importable Python package, a library
that also contains Parthenon's Python package and any Python code the library provides.
Applications are Python scripts that import the package to set up and run a problem.

.. code:: cmake

   parthenon_add_python_module(_myapp
     PACKAGE myapp
     SOURCES my_bindings.cpp
     PYTHON_SOURCES myapp/__init__.py
     LINK_LIBRARIES myapp-lib
     OUTPUT_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR}
     STUBS)

creates the package ``myapp`` in ``OUTPUT_DIRECTORY`` (which defaults to
``CMAKE_CURRENT_BINARY_DIR``):

.. code:: text

   myapp/
     __init__.py                the PYTHON_SOURCES
     _myapp.<ext>               the module, built from SOURCES and the Parthenon bindings
     parthenon/                 Parthenon's Python package (myapp.parthenon)
     _myapp/*.pyi, py.typed     type stubs (with STUBS)

With ``OUTPUT_DIRECTORY`` on the Python path (e.g., for a script in that directory),
``import myapp`` works. ``PYTHON_SOURCES`` are copied into the top level of the package, and are copied
again when they change. With ``INSTALL_DESTINATION <dir>``, the package is installed to
``<dir>``. When Parthenon is installed, ``find_package(parthenon)`` makes
``parthenon_add_python_module`` available (after Python and nanobind have been found).

The module must call ``ImportParthenon``, which registers the Parthenon bindings as the
submodule ``_myapp.parthenon``, before using any Parthenon type:

.. code:: cpp

   #include <parthenon_nanobind.hpp>

   NB_MODULE(_myapp, m) {
     parthenon::python::ImportParthenon(m);
     m.def("Initialize", &my_package::Initialize);
     nanobind::class_<MyDriver, parthenon::MultiStageDriver>(m, "MyDriver")
         .def(nanobind::init<parthenon::ParameterInput *, parthenon::ApplicationInput *,
                             parthenon::Mesh *>());
   }

The ``parthenon`` subpackage re-exports these bindings and adds Python helpers such as
``parthenon.cli``. It imports the module itself, so the package's code only needs
``from . import _myapp, parthenon``, and applications ``from myapp import parthenon``.

With ``STUBS``, type stubs of the module are generated with nanobind's ``stubgen`` after
it is built. Since ``parthenon`` re-exports the module's ``parthenon`` submodule, type
checkers see the same types in both, so application code that passes
``parthenon.ParameterInput`` objects to the module's functions can be type checked. Since
the stubs are generated by importing the module, the build must be able to import it.

Command line
------------

``parthenon.cli`` parses the same command line as a C++ Parthenon executable
(``-i``, ``-r``, ``-a``, ``-d``, ``-p``, ``-c``, ``-m``, ``-t``, ``-w``, ``--kokkos-*``
arguments, and ``block/par=value`` overrides), with ``argparse``. Applications can add
their own options:

.. code:: python

   from myapp import parthenon

   parser = parthenon.cli.make_parser(description="My application")
   parser.add_argument("--my-option")
   args = parthenon.cli.parse_args(argv, parser)
   args.namespace.my_option             # the application's options
   pin = args.parameter_input()         # input file with the overrides applied
   pman.ParthenonInitEnv(pin, args.options)

Errors are reported by ``argparse``, which exits with status 2. ``-c`` prints the
configuration and exits with status 0 (the C++ executables exit with an error status).
An application that sets its parameters in Python can make the input file optional with
``parse_args(argv, parser, require_input=False)``, and pass its parameters to
``args.parameter_input(base)``, which reads the input file (if any) and applies the
overrides on top of ``base``. Parameters set in Python keep their Python type, which must
match the type C++ reads them as (e.g., ``1.0`` for a ``Real``).

Running with MPI
----------------

Like a C++ executable, a Python application runs in parallel by launching it on every
rank, e.g.,

.. code:: bash

   mpirun -np 4 python run_advection.py -i parthinput.advection

MPI (and Kokkos) are initialized by ``ParthenonInitEnv``. Each rank runs the whole
script; problem generators and other callbacks are only called for the blocks of the
rank, and anything else (e.g., printing) happens on every rank.

Using the bindings
------------------

The Python advection example (``example/advection/python``) is a complete example. The
package ``advection`` is a library that provides the C++ advection package and driver
(and ``advection.parthenon``). The application, ``run_advection.py``, imports it and
implements ``ProcessPackages``, the problem generators, and the main program in Python.
Without an input file, it uses ``advection_input()``, which sets the parameters of
``parthinput.advection`` in Python. The build puts ``run_advection.py`` next to the
package and creates a launcher, ``<build>/example/advection/advection-example-py``, that
runs it with the same command line as ``advection-example``. The main program looks like

.. code:: python

   import advection
   from advection import parthenon

   pin = parthenon.ParameterInput()
   pin.load_file("parthinput.advection")
   pin["parthenon/time/tlim"] = 0.5

   pman = parthenon.ParthenonManager()
   pman.app_input.ProcessPackages = process_packages
   pman.app_input.ProblemGenerator = block_problem_generator
   pman.app_input.RegisterDefaultReflectingBoundaryConditions()

   pman.ParthenonInitEnv(pin, parthenon.RuntimeOptions(run_dir="output"))
   pman.ParthenonInitPackagesAndMesh()
   driver = advection.AdvectionDriver(pman.pinput, pman.app_input, pman.pmesh)
   driver.Execute()
   del driver
   pman.ParthenonFinalize()

``ParthenonInitEnv(pin, opts)`` corresponds to the C++ overload described in
:ref:`parthenonmanager` (the manager keeps a copy of ``pin``); the command line version
``ParthenonInitEnv(["prog", "-i", "input"])`` is also available.
``ParameterInput.load_file`` does not use MPI, so it can be used before Parthenon is
initialized, unlike the C++ ``ParameterInput(filename)`` constructor.

Field data is accessed on the host through packs, which play the role of a
``SparsePack`` for Python. Like a ``SparsePack``, variables are identified by base name:
``mb.pack(names)`` packs the named variables of a block, including all members of a
sparse pool that are allocated on the block, and ``mb.pack(flags=[...])`` packs all
allocated variables that have all of the given metadata flags. The pack is a context
manager: entering it copies the variables to host mirrors, inside it ``pack[name]`` is a
numpy array of a dense variable indexed ``[component, k, j, i]`` (all tensor dimensions
are flattened into ``component``), and exiting it copies the data back to the device.
Members of a sparse pool are accessed as ``pack[name, sparse_id]``, and
``pack.sparse_ids(name)`` lists the sparse IDs allocated on the block. On host-only
builds the mirrors are the device data, so nothing is copied. Arrays are only valid
inside the ``with`` block.

.. code:: python

   def problem_generator(mb, pin):
       (ks, ke), (js, je), (ib, ie) = mb.bounds(parthenon.IndexDomain.interior)
       x1 = mb.coords.Xc(1)  # cell centers of the entire block, including ghosts
       with mb.pack(["advected", "v"]) as pack:
           pack["advected"][:, ks : ke + 1, js : je + 1, ib : ie + 1] = ...
           pack["v"][1, ks : ke + 1, js : je + 1, ib : ie + 1] = ...  # second component

       with mb.pack(["my_sparse_pool"]) as pack:
           for sparse_id in pack.sparse_ids("my_sparse_pool"):
               pack["my_sparse_pool", sparse_id][...] = ...

MeshData packs
^^^^^^^^^^^^^^

A ``MeshData`` (e.g., the argument of a ``MeshProblemGenerator``) is packed the same way
with ``md.pack(names)`` or ``md.pack(flags=[...])``, but its arrays are indexed
``[block, component, k, j, i]``. Since the data of a variable is only contiguous within
each block, entering the pack gathers the blocks into a single buffer on the device,
which is contiguous over all blocks, and copies it to the host; exiting copies it back
and scatters it to the blocks. A member of a sparse pool only has rows for the blocks it
is allocated on, and ``pack.block_indices(name, sparse_id)`` gives the index in the
``MeshData`` of the block of each row (for dense variables, row ``b`` is block ``b``).

``md.NumBlocks()``, ``md.block(b)``, and ``md.blocks`` give access to the blocks,
``md.bounds(domain)`` gives the index ranges (which are the same on all blocks), and
``md.coords.Xc(dir)``, ``Xf(dir)``, and ``Dx(dir)`` give the coordinates of all blocks as
arrays indexed ``[block, index]`` (``[block]`` for ``Dx``).

.. code:: python

   def mesh_problem_generator(mesh, pin, md):
       (ks, ke), (js, je), (ib, ie) = md.bounds(parthenon.IndexDomain.interior)
       x1 = md.coords.Xc(1)[:, ib : ie + 1]  # [block, i]
       with md.pack(["advected"]) as pack:
           pack["advected"][:, :, ks : ke + 1, js : je + 1, ib : ie + 1] = ...

The advection example implements both versions of the problem generator, selected with
``--pgen block`` (the default) or ``--pgen mesh``.

Notes:

* Python callables may be assigned to the ``ApplicationInput`` hooks and to the
  ``StateDescriptor`` callbacks (``FillDerivedBlock``, ``EstimateTimestepBlock``, ...).
  They are called with the GIL held; ``Driver.Execute`` releases the GIL while
  C++ is running.
* ``StateDescriptor.AddParam`` stores ``bool``, ``int``, ``float``, and ``str`` values as
  the corresponding C++ types, so they can be read with ``Param<T>`` in C++. Other Python
  objects are stored as Python objects.
* Drivers and any other objects holding simulation data must be deleted before
  ``ParthenonFinalize``. ``ParthenonFinalize`` drops the Python callbacks and package
  parameters held by the manager and mesh.
* ``ParameterInput`` getters finalize parsing, after which parameters can no longer be
  added with ``add`` or ``load_file`` (as in C++).
